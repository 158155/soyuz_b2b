# AI Product Card Generator

Прототип сервиса для генерации черновика карточки товара
по входным данным. Принимает JSON
о товаре, отправляет его в LLM и возвращает SEO-заголовок,
SEO-описание, ключевые характеристики, поисковые запросы и
commercial-блок для менеджера.

## Что делает сервис

- Принимает данные о товаре в формате JSON (один объект или массив).
- Передаёт их в выбранную LLM через OpenAI-совместимый API.
- Формирует черновик карточки: SEO-заголовок, SEO-описание,
  структурированный список характеристик, 3–5 поисковых запросов,
  commercial-блок.
- Сообщает, каких полей не хватает (`missing_fields`) — как путей
  входного JSON, например `specs.диапазон измерений`.
- Отдаёт результат в Markdown или JSON (скачивание), либо показывает
  на странице.

## Установка

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# заполнить LLM_API_KEY и при необходимости LLM_BASE_URL / LLM_MODEL
```

### uv (альтернатива)

Если установлен [uv](https://docs.astral.sh/uv/):

```bash
uv sync
cp .env.example .env
# заполнить LLM_API_KEY и при необходимости LLM_BASE_URL / LLM_MODEL
```

`uv sync` создаст `.venv` и установит зависимости из `uv.lock`
(зафиксированные версии). Запуск — тот же: `uvicorn app.main:app --reload`
(или `uv run uvicorn app.main:app --reload`).

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_BASE_URL` | Base URL OpenAI-совместимого API | `https://api.openai.com/v1` |
| `LLM_API_KEY` | Ключ API (не коммитится) | — |
| `LLM_MODEL` | Имя модели | `gpt-4o-mini` |
| `LLM_TIMEOUT` | Таймаут запроса, сек | `120` |
| `LLM_MAX_TOKENS` | Лимит токенов ответа | не задан |
| `LLM_MAX_CONCURRENCY` | Максимум одновременных вызовов LLM | `1` |

Подходит любой OpenAI-совместимый провайдер: OpenAI, локальная модель,
Ollama (`LLM_BASE_URL=http://localhost:11434/v1`), vLLM и т.п.

## Запуск

```bash
uvicorn app.main:app --reload
# открыть http://127.0.0.1:8000
```

Загрузите JSON-файл с одним товаром или массивом товаров. Результат
показывается на странице; для скачивания в MD/JSON используйте
кнопку на странице (или `/export` ).

## Формат входных данных

Контракт рассчитан на структуру из задания:

```json
{
  "name": "Манометр показывающий DM Ø2",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

- `specs` — плоский словарь «характеристика → значение».
- `extra="allow"`: неизвестные поля верхнего уровня принимаются и не
  попадают в характеристики.
- Отсутствующие/пустые значения (`null`, `""`, `[]`, `{}`) попадают
  в `missing_fields`.
- Произвольная вложенность `specs` **не гарантируется** (см. «Ограничения»).

## API

- `GET /health` — проверка доступности.
- `POST /generate` — генерация карточки для одного товара из JSON-тела.
  Возвращает JSON `GenerateResponse`.
- `POST /generate-file` — загрузка JSON-файла, результат в HTML.
- `POST /export` — загрузка JSON-файла, скачивание результата в MD или JSON.

Ошибки API:

- `422` — некорректные входные данные (детали — в логах, не в ответе).
- `502` — LLM недоступна или вернула невалидный ответ.
- `500` — внутренняя ошибка (детали — в логах).

## Архитектура

- `app/main.py` — фабрика приложения, обработчики исключений.
- `app/config.py` — настройки (pydantic-settings), кэш async-клиента OpenAI.
- `app/constants.py` — SEO-лимиты, допустимые форматы вывода.
- `app/fields.py` — нормализация путей полей, признаки метаданных.
- `app/schemas.py` — Pydantic-модели входа/выхода.
- `app/llm.py` — async-клиент LLM, JSON-mode с fallback, семафор, извлечение JSON.
- `app/prompts.py` — системный и пользовательский промпты.
- `app/service.py` — доменная логика: детект пропусков, нормализация
  характеристик, merge missing, retry, `generate_card`.
- `app/markdown.py` — Markdown-представление карточки.
- `app/services/file_ingest.py` — чтение/валидация JSON, пакетная генерация.
- `app/services/export.py` — форматы вывода, безопасное имя файла, download.
- `app/api/routes_pages.py` — страницы.
- `app/api/routes_api.py` — API-эндпоинты.
- `templates/` — Jinja2-шаблоны.

Поток: HTTP → `routes_api` → `service.generate_card` → `llm.chat_json`
→ пост-обработка → `ProductCard` → Markdown/JSON или HTML.

## Принятые решения

- **Контракт входа явный, но терпимый.** Верхний уровень
  `name/manufacturer/description/specs`; `extra="allow"` не роняет
  запрос при лишних полях. Полностью независимый контракт
  (произвольный набор полей и вложенности) — вне рамок MVP.
- **`missing_fields` — пути входного JSON**, а не человекочитаемые
  названия. Это согласовано с рекурсивным обходом входа и позволяет
  точно указать, чего не хватает.
- **Метаданные и характеристики разведены** в `app/fields.py`:
  `name/manufacturer/description/specs` не попадают в `key_features`.
  Один источник правды используется и в промпте, и в пост-обработке.
- **Async везде, где есть I/O.** LLM-клиент на `AsyncOpenAI`,
  эндпоинты `async def`. Чистая логика (нормализация, сборка
  `ProductCard`, форматирование) остаётся sync — ей нечего ждать.
  Это упрощает добавление async-БД/кэша/брокера в будущем.
- **Семафор вокруг вызова LLM** (`LLM_MAX_CONCURRENCY`, по умолчанию 1).
  Товары внутри файла обрабатываются последовательно; семафор
  защищает от параллельных вызовов между HTTP-запросами, чтобы не
  перегружать локальную модель. Семафор привязан к текущему event
  loop и пересоздаётся при его смене — безопасно для тестов и hot-reload.
- **Retry с конкретной проблемой.** При невалидном ответе LLM вторая
  попытка получает точное описание: какое поле, фактическая длина,
  дельта (`seo_description: 1445 символов (нужно 800–1200, сократи
  на ~245)`), и просьбу переписать только проблемные поля.
- **Без обрезки и дополнения `seo_description`.** Детерминированная
  обрезка теряет ценность текста и требует последующей проверки
  контент-менеджером; дополнение рискует «натянуть» текст. Если модель
  не сходится по длине — это видно в `notes` и в логах, а не маскируется.
- **Ошибки не утекают наружу.** `/generate` отдаёт `502` для
  `GenerationError` и `500` для прочего, без `str(exc)` в теле;
  детали — в логах. `/export` отдаёт JSON-ошибки, `/generate-file` —
  HTML (это страница).

## Промпты

- **Системный промпт** задаёт жёсткие правила: использовать только
  данные из входного JSON, не выдумывать характеристики, при
  отсутствии — «данных нет»; формат ответа — строгий JSON; длины
  SEO-полей; 3–5 поисковых запросов; `key_features` — только
  технические характеристики (`поле: значение`).
- **Пользовательский промпт** — сериализованный входной JSON плюс
  инструкция вернуть только JSON.
- **Retry-промпт** — базовый промпт плюс конкретная проблема
  валидации и просьба переписать только проблемные поля, не трогая
  корректные `key_features`, `missing_fields`, `commercial_block`, `notes`.

## Объём MVP

Задание рассчитано на 2–4 часа, поэтому часть вещей сознательно не
делалась — не потому, что они не нужны, а потому что для прототипа
они не критичны. Ниже — три категории: что отложено осознанно
("не делал в рамках MVP"), какие есть технические ограничения
контракта, и что можно улучшить дальше.

### Что сознательно не делалось в рамках MVP

- **Обработка ошибок LLM по типам** (rate limit, timeout,
  недоступность модели) с backoff и ретраями на уровне транспорта.
  Сейчас есть только retry на невалидный ответ; сетевые ошибки
  пробрасываются.
- **Закрытие клиента LLM при shutdown** через `lifespan` с
  `await client.close()`. Для локального прототипа не критично.
- **Очередь задач и параллельная пакетная генерация.** Товары внутри
  файла обрабатываются последовательно; для больших объёмов нужна
  очередь и контроль лимитов провайдера.
- **Структурированный вывод через function calling / JSON Schema**
  вместо `response_format=json_object`.
- **Мониторинг, метрики, трейсинг** вызовов LLM.
- **Хранение результатов, история генераций, повторный экспорт.**
- **Очеловечивание `missing_fields`** в UI и Markdown (сейчас — пути
  входного JSON).
- **Полноценная CMS, админ-панель, БД, деплой** — по заданию не
  требуются.

### Технические ограничения

- **Зависимость от модели.** Требование «`seo_description` 800–1200
  символов» выполняется не всеми моделями одинаково. На компактных
  моделях (проверялось на Ollama/gemma4:31b,Ollama/nemotron-3-super
  local/Qwen3.5) retry с уточнением «сократи на ~N»
  может не сходиться: модель переписывает текст, и длина не уменьшается
  (в тестах: 1426 → 1445 символов). На более мощной модели тот же
  уточнённый промпт отрабатывает с первой повторной попытки.
  Рекомендация: выбирайте модель, устойчиво следующую инструкциям
  по длине.
- **Стоимость retry на коммерческих моделях.** Retry (до 2 попыток)
  рассчитан на то, что повторная попытка сходится. На бесплатных
  моделях это не всегда так, и на платной модели такое поведение
  означает двойной расход токенов за товар без гарантии результата.
  Для MVP это приемлемо (объёмы малы); в продакшене — см. «Возможные
  улучшения».
- **Произвольная вложенность `specs` не гарантируется.** Контракт:
  `specs` — плоский словарь. `detect_missing` рекурсивен и не упадёт,
  но `feature_label` для `specs.a.b` даст `a.b`, и это поведение
  не гарантируется.
- **`missing_fields` — пути, не человекочитаемые названия.**
  Очеловечивание — на стороне рендера (Markdown/UI), не в модели.
- **Товары внутри файла обрабатываются последовательно.** Ошибка
  одного товара не прерывает остальные.
- **Локальный прототип**, без БД/CMS/деплоя, без мониторинга
  и метрик production-уровня.

### Возможные улучшения

- **Управление стоимостью retry:** ретраить только ошибки, где повтор
  помогает (невалидный JSON, структурные проблемы), и не ретраить
  ошибки длины `seo_description`, где модель на бесплатных моделях
  не сходится, — вместо этого писать фактическую длину в `notes`;
  бюджет токенов на товар; кэш успешных ответов по хэшу входа.
- **Разные модели для первой и повторной попытки:** дешёвая/локальная
  для первой, более сильная для retry.
- **Очередь задач** и параллельная пакетная генерация большого числа
  товаров (с учётом семафора и лимитов провайдера).
- **Обработка ошибок API по типам:** rate limit, timeout, недоступность
  модели — с backoff и ретраями на уровне транспорта.
- **Структурированный вывод через function calling / JSON Schema**
  вместо `response_format=json_object` — жёстче гарантирует схему.
- **Очеловечивание `missing_fields`** в UI и Markdown.
- **Хранение результатов, история генераций, повторный экспорт.**
- **Мониторинг, метрики, трейсинг** вызовов LLM.
- **Закрытие клиента LLM** через `lifespan` с `await client.close()`.
